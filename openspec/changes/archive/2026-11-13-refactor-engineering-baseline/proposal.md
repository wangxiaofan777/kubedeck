## Why

当前代码是在技术验证阶段逐次堆起来的：进程启动、数据库初始化、后台任务与 HTTP 服务混在 `main` 中；接口层单个文件同时承担路由、参数解析、响应写入与集群访问；前端页面组件同时管理布局、查询、轮询与选中状态。与此同时，仓库缺少统一的格式化/静态检查入口，CI 中的数据层集成测试因没有数据库而静默跳过，全新检出还会因为缺少前端产物占位而直接编译失败。

继续叠加认证、集群登记与写操作之前，需要先把工程基线固定下来，否则结构耦合与检查缺口会在后续每次改动中被放大。

## What Changes

- **结构调整**：拆分启动编排、接口处理、集群注册表与仓储职责；对外 API 契约与页面信息架构保持不变。
- **可复现构建**：修复全新检出与清理后无法编译的问题；统一本地与 CI 的构建入口。
- **质量闸门**：引入后端格式化与静态检查、前端 lint/格式检查；CI 连接真实 PostgreSQL 执行数据层集成测试，并提供与 CI 一致的本地检查命令。
- **运行基线**：启动配置在监听前完成校验并快速失败；新增就绪探测；明确退出顺序；修正安全响应头以兼容前端样式；审计保留期读取失败时停止清理；命名空间列表完整分页。
- **文档**：更新根 README 与 AGENTS 的当前状态、目录结构与快速开始。

不改变产品的信息架构、页面流程与现有 API 语义；不引入认证、集群登记写接口、写操作或实时推送。

## Capabilities

### New Capabilities

- `engineering-baseline`：可复现构建、统一质量闸门、启动配置校验、就绪探测与优雅退出、安全响应头兼容、审计保留期失败保护。

### Modified Capabilities

（无，本变更不修改现有能力的需求）

## Impact

- **代码结构**：`cmd/server`、`internal/{api,app,config,kube,store}` 与 `web/src` 的包/目录划分调整；无破坏性 API 变更。
- **HTTP 接口**：新增 `/readyz`；`/healthz` 保持存活语义；现有响应字段不变。
- **构建与 CI**：Makefile、GitHub Actions、前端 devDependencies 调整；Docker 构建流程保持单镜像交付。
- **数据库**：不新增业务表；迁移记录表增加校验和列，用于检测已执行迁移被篡改。
- **运维**：错误配置会阻止启动；编排可基于 `/readyz` 决定是否引流；审计分区清理在配置不可读时不再继续。
- **安全**：仅调整响应头与输入校验，不放宽任何授权边界；Impersonation-only 约束保持不变。
