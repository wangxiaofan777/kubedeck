# 提案：收敛运行时可靠性缺陷

## 背景

MVP 已归档，但代码审阅发现若干会在真实使用中必然复现的问题：实时 watch 约 10 秒被 HTTP 客户端超时掐断、日志跟随在 30–60 秒被服务端超时截断、审计导出被静默截断为 100 条、补偿队列溢出时静默丢弃审计、Pod 日志与驱逐的命名空间准入与实际操作对象可能不一致。这些问题不改变产品形态，但直接推翻「实时」「可跟随」「审计可信」三项核心承诺。

## 目标

1. 长连接（watch、日志 follow）不再被请求级超时中断。
2. 审计导出返回完整结果，保留期真正生效且完整性校验能处理已删除的历史前缀。
3. 审计队列不可用时，高风险写操作被明确拒绝而不是静默丢弃。
4. 平台准入与 apiserver 实际操作使用同一个命名空间，消除租户边界歧义。
5. 收紧 kubeconfig 文件读取、上游错误透传与平台角色约束。

## 非目标

- 不引入 informer 缓存（作为独立决策，另行评估）。
- 不新增 Agent 隧道或改变 Impersonation 授权模型。
- 不重做审计存储结构；只补充保留期维护与校验边界。

## 影响

- `internal/kube`：watch 使用独立无总超时的客户端；拒绝 `tokenFile`。
- `internal/api`：日志 follow 豁免超时并延长写截止时间；审计导出独立上限；写请求在审计降级时返回 503；命名空间只取路径参数；上游错误脱敏；平台角色按动词收敛。
- `internal/audit`：暴露队列健康状态与丢弃计数，降级时拒绝高风险写。
- `internal/store`：保留期删除任务接线；链校验支持截断前缀；补查询索引。
- `internal/app`：周期维护任务与优雅退出时刷写补偿队列。
